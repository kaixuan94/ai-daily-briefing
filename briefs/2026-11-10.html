1.1 Anthropic 发布 Claude Fable 5.2 与 Mythos 5.2：更强、降价两成，订阅越久重置越多

  • 核心观点：@claudeai 发布 Fable 5.2 与 Mythos 5.2，称在编程、推理、视觉上有提升；预发布测试中，Fable 5.2 仅凭一段提示就设计出 3 款可用的电子设备（含一个家庭语音助手 Hub）。@dotey 的中文整理：两者是同一模型，区别只在护栏。Fable 加了网络安全与生物方面的护栏、面向所有付费用户；Mythos 只开放给通过审核的机构。输出速度比 5.1 最多快 30%，API 从 $10/$50 降到 $8/$40；Max/Ultra 按订阅时长送 1–3 次「Fable 额度重置」（@bcherny：订阅越久送得越多）；Pro 在 11/9–11/16 可从套餐额度里用 Fable。@Fei2411 提醒 Terminal-Bench 4.0 上的提升不大。

1.2 Fable 时代的「规划/执行分离」与提示词技巧

  • 核心观点：@AlexFinn 的用法是用 Fable 5.2 做规划与头脑风暴，把任务拆成极细的清单写进任务管理器，再交给 Opus 5.5 逐条执行，用 Sonnet/Haiku 子 Agent 做测试，效果更好也更省 token。@mattpocockuk：让 Agent 追问需求时讲「为什么」而不是「做什么」（先描述问题，而不是先给方案），否则 Agent 会默认方案已定，只追问实现细节。@kentcdodds 推荐一条提示：「找出应用里所有隐式状态机，在不破坏任何东西的前提下兼顾 UX/DX/AX，并把状态机显式化」。@dotey：换新模型正好用来清理精简提示词（「通读整个项目，找出损坏、不一致、低效或不再需要的东西，修复有把握的，其余列出来给我审」）。
  • 关键方法/工具：Fable（规划）→ Opus（执行）→ Sonnet/Haiku（测试）的分层；「问题先行」的需求追问；隐式状态机显式化提示词。
  • 可行动点：今天就把一个中型需求按「Fable 规划 + 便宜模型执行」跑一遍，记录 token 与返工次数，与单模型方案对比。
  • 原帖链接：https://x.com/AlexFinn/status/2119891924316454975 ；https://x.com/mattpocockuk/status/2119888414736859356 ；https://x.com/kentcdodds/status/2119812466037428392 ；https://x.com/dotey/status/2119894229581508868

2.2 zkyo：Telegram Bot 从 Hermes 换到 Cindy，长程任务 token 消耗明显下降

  • 核心观点：@zkyo 实测，换成 Cindy 后，无论 Harness 用 Codex 还是 Pi，许多任务都快得多、更省 token。长程任务差距尤其大：开 PR、做完整功能视频时，Cindy 一轮用不到 272k，Hermes 已经压缩上下文 2–3 次。他们内部有 CI 机、打包机等多台机器，所以很看重「一个入口、任务可开在任意设备」的用法。
  • 关键方法/工具：Cindy、Hermes、Codex / Pi Harness。
  • 可行动点：用同一个长任务（如「开一个 PR」）对比自己在用的 Agent 的上下文压缩次数和总 token，再决定主力。

2.3 Barret：DeepSeek Harness 本质是面向 Agent Runtime 的 IoC 模块系统

  • 核心观点：@Barret_China 读完源码后认为，DeepSeek Harness 和企业级 Node.js 框架 Tegg 在架构上高度相似：用 Service 注册 + inject 管理依赖；插件生命周期由 Fiber 管理（PENDING → LOADING → ACTIVE → UNLOADING → DISPOSED），副作用由 Effect 托管，并支持依赖驱动的动态加载与卸载。他的结论：依赖注入、生命周期、AOP 等经典服务端工程思想，正在 Agent Runtime 里被系统性复用。
  • 关键方法/工具：DeepSeek Harness 插件机制（Service / inject / Fiber / Effect）。
  • 可行动点：写 Harness 插件时按「Service 提供者 / 消费者」拆分能力，把资源注册放进 Effect，方便热卸载。
  • 原帖链接：https://x.com/Barret_China/status/2119787495638618577
  • 来源标注：【账号池】@Barret_China

2.4 AI 代码 Review 不过来怎么办：分级审核 + 不让 AI 给自己判卷

  • 核心观点：@hocyzon 给出四步：① 控制生成过程，先拆模块、定接口，用 TDD 先写测试；② 按风险分级审核，高风险（交易、权限）必须人审，中风险用 2–3 个不同模型交叉 Review、有冲突再交给人，低风险 AI 自动审 + 人工抽检；③ 写代码、出测试、评质量的分开由不同 Agent 负责，避免同源判断；④ 保留静态分析、单测、集成、回归、端到端等质量门。@changloria0816 补充：Demo 人人能做，上线靠的是写测试、做 Code Review、识别 Agent「一本正经地出错」。
  • 关键方法/工具：风险分级 Review；多模型交叉审查；历史缺陷评测集。
  • 可行动点：给仓库加一份 REVIEW_POLICY.md，标明哪些目录属于高风险、必须人审。
  • 原帖链接：https://x.com/hocyzon/status/2119707598484087266 ；https://x.com/changloria0816/status/2119792943435551151
